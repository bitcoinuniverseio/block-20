Conformance and fixtures

Test the writer behavior you are relying on.

Source-driven payload-shape schema and test vectors for client and backend teams. These vectors describe current InScribe output and API behavior, not a universal indexer consensus suite.

Machine-readable shape
JSON Schema, draft 2020-12
Test target
Returned inscriptionJson and API behavior, not only the original request.
Dynamic source
Normal mint includes a live block hash, so assert relation to the response rather than a hard-coded hash.
What this suite does not prove. Passing these vectors does not show that an independent indexer will recognize a ticker, enforce supply, accept an amount, or reach the same balance state. Add the chosen reader's own compatibility tests.

Schema

Validate emitted shapes without inventing semantic rules.

The JSON Schema constrains the three shapes emitted by the current writer. It intentionally models numeric-looking payload fields as strings and does not claim they are positive integers or accepted by every reader.

Schema locationUse in automated validation
schemas/block20-inscribe-payload.schema.json

What it validates

Literal p, supported op shapes, required field presence, string representations, and the absence of extra fields in current writer output.

What it intentionally leaves open

Ticker rules, arithmetic rules, supply state, block ordering, hash validity, transfer accounting, and external indexer acceptance. Those are outside the writer-only contract.

Zero or decimal vectors are regression observations, not a recommendation. The public API currently accepts 0 and decimal amount values. A production client should impose the target reader's documented semantic rules rather than treating API acceptance as token validity.

End-to-end matrix

Complete the tests the writer alone cannot provide.

Run these against a controlled environment with an intended wallet, mempool source, broadcast source, and compatible reader. Do not test money-moving flows only with mocked JSON.

  • Normal deploy, mint, and transfer order creation with explicit valid receiver addresses.
  • Payment detection using an unconfirmed eligible UTXO and a confirmed eligible UTXO.
  • Reveal success, including inspection of on-chain inscription content type and parsed JSON.
  • Receiver fallback prevention in the client, including a rejected empty receiver address.
  • Reveal retry and terminal error user experience without creating a duplicate payment.
  • One-hour no-payment expiry and the product behavior for a late qualifying payment.
  • Target indexer recognition, supply/mint accounting, and transfer outcome for every supported operation.
  • Network mismatch prevention between receiver, wallet, mempool source, and deployment configuration.
