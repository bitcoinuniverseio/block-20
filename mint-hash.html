Hash implementation

Mint hash reference

Use a Bitcoin block ID, not a transaction identifier.

For a normal BLOCK-20 mint through Bitcoin Universe Inscribe, the hash field is a server-selected snapshot of the configured Bitcoin chain tip. It is never a client-selected transaction ID, inscription ID, Merkle root, or payload digest.

Do not send a mint hash in POST /block20/order. The public order contract does not use a caller-provided hash. For action: "mint", the writer fetches its own current tip hash and serializes that value into the inscription. Always inspect the returned payload before payment.

The short answer

Exactly which hash belongs in a mint?

Use the canonical block-hash string returned by a trusted Bitcoin node or compatible Mempool API for the target chain. In the shipped server flow, it is obtained by reading the current tip height and then resolving that height to its block hash.

Use this

One Bitcoin block hash

A 32-byte Bitcoin block identifier in the normal human-facing hexadecimal representation. The interoperability profile below uses 64 lowercase hexadecimal characters with no prefix or whitespace.

Do not use this

Not a transaction or inscription ID

Do not substitute the funding transaction ID, reveal transaction ID, Ordinals inscription ID, a block height, a previous block hash, a Merkle root, or a hash you calculated from the JSON.

Understand this

It is a snapshot, not a promise

The value records the tip observed while creating the order. It does not identify the block that later confirms the reveal, and it is not proof that an independent reader will accept the mint.

Current writer sequence

How the server selects and freezes the hash.

The implementation makes two reads against the configured Mempool-compatible source. The resulting value is recorded with the order and copied into the exact JSON bytes used to build the inscription.

Select the configured Bitcoin network

The server's global Bitcoin configuration chooses the Mempool base URL. Test mode selects the configured testnet source, otherwise the configured mainnet source. This selection is independent of the request body.

Read the current tip height

The writer requests /blocks/tip/height from that source. This produces a height snapshot, not a client-provided value.

Resolve that height to a block hash

The writer requests /block-height/{height}, trims the returned text, and treats it as the mint hash. It does not calculate, reverse byte-order, uppercase, or otherwise transform the value.

Serialize the mint payload

The writer emits { p, op, tick, amt, hash } through JSON.stringify, then stores the same hash as blockHash on the order record.

Fund and reveal later

Payment detection and reveal occur after the snapshot. They do not refresh the hash, add the height, or replace the payload when the chain advances.

There is an intentional timing boundary. A new block can arrive between API reads, between order creation and payment, or before reveal. The current order response retains the hash but not the source URL or selected height. If your product needs a stricter freshness window, record the height and source beside the order and create a new order when the rule is no longer met.

Verification procedure

Verify the hash before and after the reveal.

Make the mint hash a first-class audit value. A wallet or client should show it in the review state and retain it with the order record, instead of treating it as hidden server metadata.

Before funding

  1. Create the order without a client hash.
  2. Parse the returned inscriptionJson.
  3. Assert payload.op === "mint".
  4. Assert payload.hash === order.blockHash.
  5. Require the canonical 64-character lowercase hexadecimal form in your client policy.
  6. Record the order timestamp, observed hash, source context, and target reader.

After reveal

  1. Inspect the reveal inscription's bytes and content type.
  2. Parse its JSON and compare the hash to the immutable order record.
  3. Resolve the hash on the intended network and reader source.
  4. Apply the reader's documented active-chain, reorganization, and freshness rules.
  5. Only then treat reader visibility or token accounting as an application-level result.
Minimal validation relationshipClient or test harness
const payload = JSON.parse(order.inscriptionJson)

assert(payload.p === 'block-20')
assert(payload.op === 'mint')
assert(payload.hash === order.blockHash)
assert(/^[0-9a-f]{64}$/.test(payload.hash))

// Resolve against the intended network's configured block source.
const block = await getBlock(payload.hash)
assert(block.id === payload.hash)
Keep the equality check simple. The key invariant for this server-assisted path is exact string equality between the persisted order's blockHash and the parsed hash in the inscribed JSON. Do not normalize, byte-reverse, or substitute another identifier before comparison.

Failure and policy cases

Do not silently repair a mint hash.

A changed hash changes the inscription bytes. When a policy cannot be satisfied, create and review a new order instead of mutating an existing order or trying to reuse a payment instruction.

ConditionSafe product response
Tip lookup fails during mint creationDo not create or fund the normal mint order. Surface the upstream failure and retry order creation after the source is healthy.
Returned hash is empty, malformed, or mismatched with payload JSONTreat the order as invalid for your client policy. Do not open a payment action. Capture evidence and investigate the configured source.
Wallet network and configured tip source differStop the flow. Resolve the deployment configuration before generating a new order. The server's tip source is selected globally, while receiver-derived order network can differ.
Product or reader requires a newer hash before paymentCancel the payment intent and generate a new order. Never replace only the hash in a stored payload or reuse an old commit address for unrelated funds.
Reader reports a reorganization or no active-chain matchApply that reader's explicit policy. The current writer does not rewrite the existing mint payload or re-anchor it automatically.
