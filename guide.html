Integration guide

Build a safe product flow around the actual order model.

Use this guide when your app creates BLOCK-20 orders through Bitcoin Universe Inscribe. It focuses on destination safety, user confirmation, lifecycle observation, and evidence needed for support.

Prerequisite
A compatible wallet or manual Bitcoin payment path, funded on the intended network.
Required client record
Order ID, receiver address, payment details, payload, and transactions.
Final verification
On-chain reveal plus a compatible reader or indexer result.

Product flow

Seven steps from intent to verification.

Do not condense these stages into a generic "send" button. BLOCK-20 order creation, payment, reveal, and indexer interpretation are separate events with different failure modes.

Choose the reader and network first

Decide which compatible indexer or reader will evaluate the payload, and ensure the connected wallet, receiver address, server configuration, and payment path use the same Bitcoin network.

Collect and validate intent locally

Validate ticker, amount, supply, and mint limit according to your product and reader requirements. The server does not enforce many of these semantic constraints.

Require an explicit receiver address

Collect a valid user-controlled receiver address for every normal order. Display it on the review screen, and store it before calling the API.

Create one order and freeze its details

Call POST /block20/order. Use the returned inscriptionJson, blockHash, commitAddress, commitAmount, network, and expiry as the immutable payment instruction for that order.

Obtain one intentional payment

Ask the wallet to fund the returned address. Prevent duplicate submissions and do not reuse a commit address for unrelated funds.

Poll order status and surface uncertainty

Poll the public order endpoint. Show the distinctions between awaiting payment, reveal retry, terminal error, and a reveal transaction ID. Never equate an HTTP 201 with a confirmed reveal.

Verify in the intended reader

After revealTxid exists, confirm the inscription bytes and ask the selected reader or indexer for the intended result. Keep every identifier needed to reproduce the outcome.

Strong client validation

Apply the rules your product actually needs.

The server is deliberately permissive in several areas. A production client should validate user intent before creating a payment instruction, while still treating the server's returned payload as the record to display and retain.

Recommended before order creation

  • Normalize and validate the ticker with the target reader's documented rules.
  • Require a positive integer amount if that is your reader's requirement. The current API does not do so.
  • Use whole-number amount and fee-rate values. Current request parsing accepts decimals, but integer-backed persistence does not establish a reliable decimal round trip.
  • Require explicit numeric maxSupply and limitMint for deploys. Do not rely on public endpoint defaults.
  • Reject a receiver address that does not belong to the intended network.
  • Display fee rate, commit amount, and expiry with units before a wallet opens.

Do not send as client input

  • p. The writer inserts literal block-20.
  • hash for a normal mint. The server fetches and inserts its own observed tip hash. See exact selection and verification rules.
  • Assumptions that repeatCount creates multiple direct BLOCK-20 inscriptions.
  • Secrets or private keys. The server-owned commit key is internal infrastructure, not a client API field.
  • An arbitrary commit outpoint unless you understand the advanced reveal path and its safety limits.

Create and confirm

Use the returned order as the payment contract.

This request is illustrative. The dynamic order values are returned by the server. Replace the host and optional path prefix for your deployment.

  --header "Content-Type: application/json" \
  --data '{
    "action": "mint",
    "tick": "BLK",
    "amount": 1000,
    "feeRate": 5,
    "receiverAddress": "<user-controlled Bitcoin address>"
  }'

Review screen requirements

Show the action, ticker, exact inscriptionJson, returned blockHash for a mint, selected network, receiver address, commit address, commit amount in sats and BTC, service state, and expiry. Include a plain-language warning that the server performs the reveal.

Payment controls

Disable a second payment attempt after the first submission is accepted. For manual payment, clearly mark the order ID, address, amount, and network as a single-use instruction and keep the transaction ID when known.

Never silently omit the receiver. If a normal client does not send a receiver, the reveal output falls back to the backend-controlled commit address. Treat an empty receiver as a blocking validation error in the client, even though the current API does not reject it.

Mint and repeat behavior

Make automatic values visible.

Current frontend behavior and direct API behavior diverge for repeated mints. State this explicitly in any product UI so the user sees the actual route used.

Normal mint

The server observes the configured Bitcoin tip during order creation and emits that block ID as hash. A UI can explain that mint hashes are automatic, but it must show the final server-returned inscriptionJson and blockHash as the authoritative result.

The snapshot is not the reveal transaction or later confirmation block. The current server does not locally validate canonical hash shape, active-chain membership, or freshness. Use the mint-hash verification procedure.

Repeated mints

Direct repeatCount increases calculated funding but does not create multiple payloads or multiple monitor reveals. The current frontend uses a separate generic bulk endpoint for normal multi-mint UI.

Do not expose direct order repeatCount as a quantity control unless you intentionally support its current operational behavior.

Payment and audit contract

Preserve the evidence, fund one eligible output.

The public order object is intentionally not a complete recovery record. Payment detection and reveal also operate on one selected UTXO, so split or excessive funding changes the operational result.

Keep a durable issuance record

Persist the original request, returned inscriptionJson, blockHash, receiver address, fee rate, output value, commit address, commit amount, order timestamps, payment transaction and output, reveal transaction, and chosen reader or indexer.

Later public reads omit several of these fields. For a mint, retain both the hash and the exact JSON string, not just a reconstructed form.

Fund a single deliberate UTXO

Payment detection looks for one UTXO at the commit address that individually meets the minimum requirement. Several smaller outputs are not combined. When more than one eligible UTXO exists, the monitor prefers a confirmed one and selects the largest eligible value.

The reveal consumes the selected output's full value. After reveal and service fees, the residual is sent to the receiver, so do not overfund or reuse the commit address.

Direct repeatCount can magnify this funding risk. It multiplies the calculated commit amount, but direct BLOCK-20 order handling still stores one payload and triggers one reveal attempt. Do not model it as multiple independently funded mints.

Handling failures

Give users an accurate recovery path.

Some failures should be retried automatically, some require a corrected request, and some require support with the original order evidence. The public order state intentionally does not reveal every backend diagnostic.

Observed conditionProduct response
Token list unavailableOffer retry and show that token discovery depends on external indexers. Do not construct a mint from stale or unknown token information without clear user confirmation.
Latest-block lookup failsDo not create a normal mint order. The server cannot generate its required current-hash payload.
Order creation validation errorKeep the user's draft, correct the invalid field, and create a new order. Do not ask for payment without a returned order ID and payment instruction.
Payment not detectedConfirm address, network, transaction status, and that one individual UTXO meets the required amount. Retain transaction ID and vout. Do not send a second payment by default.
reveal_failedExplain that the service may retry automatically. Preserve order ID and request ID. Avoid advising the user to spend or move the commit output.
reveal_error or missing resultEscalate with order ID, receiver, commit details, payload, and transaction IDs. The public order response omits internal error detail and retry count.
Reveal transaction exists but reader does not show expected stateInspect the exact inscription bytes and use the reader or indexer version chosen at the start of the flow. This is a compatibility question, not proof that the Bitcoin transaction was absent.

Operator notes

Configuration and observability matter.

Operators of the API own a server-assisted signing process. Document and monitor the external data sources, network configuration, database, and service controls alongside the API itself.

Relevant configuration

Common backend inputs include BLOCK20_API_URL, optional comma-separated BLOCK20_API_URLS, network selection through IS_TEST, and mempool endpoints such as MEMPOOL_API_URL and its testnet equivalent.

The plural indexer fallback variable is supported by source but is not currently listed in the sample environment file. Keep configuration documentation synchronized with deployment.

What to observe

Monitor upstream indexer latency, tip lookup success, reveal broadcast failures, order-state counts, background worker liveness, request IDs, database durability, and access to the private signing material required for unresolved orders.

The pending-order monitor uses an in-process lock and scans a bounded oldest-first batch. In a multi-instance deployment, establish one active worker or a distributed lock. Use health checks and a controlled release procedure before accepting production payments.

Before release

Minimum acceptance checklist.

Test the payload, the payment lifecycle, and the final reader result together. A test that only checks JSON construction is not sufficient for a money-moving integration.

  • Request and display a valid receiver address for all normal orders.
  • Compare the returned inscriptionJson with the intended operation before payment.
  • For a mint, assert exact equality between parsed inscriptionJson.hash and returned blockHash, then apply the chosen reader's block-context policy.
  • Test order creation, payment detection, reveal success, reveal retry, expiry, and reader verification on the intended network.
  • Ensure the UI handles a 201 reveal response with revealTxid: null as a failure state, not success.
  • Save enough support evidence to reconstruct a result without relying on volatile indexer data.

Use conformance vectors to seed automated tests, then add end-to-end tests against your configured wallet, backend, and reader.
