Order lifecycle

Commit first, then a service-controlled reveal.

The BLOCK-20 order API creates server-held signing material and a funding address. Funding that address allows the service to reveal an Ordinals inscription to the selected receiver.

Payment window
Initial expiry is one hour after order creation.
Monitor cadence
Current process-local monitor runs every 10 seconds and evaluates the oldest 20 relevant orders.
Funding threshold
An eligible output is at least the returned commitAmount, with a 330-sat floor.
This is a custody boundary. The service generates and persists a private WIF and inscription script for each order, then uses that key to sign the reveal. The public order response does not expose the secret. Operators must treat the order database and reveal process as sensitive infrastructure.

Primary path

The funding and reveal sequence.

Show these steps in any integration. A successful order creation only provides an instruction to fund a commit address. It is not an on-chain inscription or an indexer-confirmed token result.

Create the order

The API serializes the payload, generates a commit address, calculates commitAmount, and stores the key material needed for reveal. Its public response begins at awaiting_payment.

Freeze and display payment details

Persist the order ID, receiver address, network, mint blockHash when present, commit address, commit amount, expiry, and exact inscriptionJson. Present only the returned payment details for this order.

Fund one dedicated commit output

Send one intentional output at or above commitAmount to commitAddress. The service does not aggregate smaller outputs, and it can choose the largest eligible UTXO at that address, so do not send unrelated funds there.

Monitor detects a UTXO

The monitor looks up UTXOs at the commit address. It accepts unconfirmed outputs, prefers confirmed outputs when available, chooses the largest eligible value, and supplies that selected outpoint to the reveal builder.

Service signs and broadcasts reveal

The server spends the commit output, embeds the inscription in the taproot script path, sends the inscription output to the receiver, and includes the configured service fee output.

Verify the reveal and reader state

Record revealTxid, inspect the on-chain inscription bytes, then query the compatible reader or indexer that determines the final protocol state.

Cost and destination

Make the payment and receiver explicit.

Most user harm in this flow comes from mixing a generic Bitcoin payment mental model with a service-controlled commit output. Make amount, destination, and custody visible before the user pays.

What commitAmount covers

It is calculated from estimated reveal fee, the resulting inscription output value, and the current 1,500-sat service fee. It is a minimum required funding amount, not a generic wallet send amount.

If a larger UTXO is selected, the reveal builder uses its actual value and sends the residual output after fees to the reveal receiver.

What the receiver controls

A nonempty valid receiverAddress determines the intended inscription output and its network when the order is constructed. Include it in every normal client request and store it locally.

The public order response does not contain receiverAddress, so an application cannot reconstruct this intent from a later order read alone.

Empty receiver fallback is not a safe default. When receiverAddress is absent or empty, reveal uses the server-generated commitAddress as the output receiver. The associated signing key is held by the backend. A nonempty malformed address can instead make reveal fail when its output is built.
Do not split or casually overfund the payment. Multiple smaller outputs are not added together to satisfy commitAmount. If a larger output is selected, its full value becomes the reveal input and the residual after fees is routed to the receiver. Keep the commit address single-purpose and record the payment transaction ID and vout.

Order states

Statuses tell you where the order is, not every diagnostic detail.

Poll GET /block20/order/:orderId after payment. The public serializer intentionally omits the private key, detailed broadcast error, and retry count.

Awaiting payment

The order was created and no eligible commit UTXO has been used for reveal.

Revealed

Broadcast produced a reveal transaction ID, exposed as revealTxid.

Reveal failed

Signing or broadcast failed. The monitor can retry this state while retry budget remains.

Reveal error

Retry budget was exhausted. Public order reads do not expose retry detail or the internal error text.

Expired

The monitor found no qualifying payment after the configured one-hour window.

Expiry is a monitor behavior

The monitor marks an overdue awaiting_payment order as expired only when it cannot find a qualifying UTXO. If a qualifying UTXO is already present after the time window, the monitor can still reveal it.

The explicit reveal API does not enforce expiresAt as a hard gate.

Failure recovery

The monitor retries reveal_failed orders up to five times. A manual reveal attempt can be used by an advanced integrator with the correct outpoint, but it should not replace normal order monitoring.

See the API reference for reveal input validation and response behavior.

Repeat-count caveat

Do not promise batch minting from a direct BLOCK-20 order.

repeatCount is an operational input, not a field in the inscribed JSON. It has a behavior that needs explicit product handling.

Current direct-order behavior. In POST /block20/order, repeatCount multiplies the calculated funding amount, but the stored order contains one inscription payload and the monitor invokes one reveal attempt. Do not document it as multiple inscriptions or repeated mints without an implementation change.
Current application behavior for multi-mint UI. The existing frontend routes normal mint quantities above one through a separate generic bulk flow with duplicated text payloads. That is a different integration surface from direct BLOCK-20 order repeatCount.

Operator checklist

Run the lifecycle as a service, not a fire-and-forget endpoint.

Successful reveal depends on database availability, signing material, the configured mempool source, broadcast access, and the background monitor process.

  • Keep the database containing generated WIFs and inscription scripts protected, backed up, and available until orders are resolved.
  • Monitor the order process, mempool reachability, reveal broadcasts, and the count of reveal_failed and reveal_error orders.
  • Run one active monitor or coordinate workers with a distributed lock. The current monitor lock is in-process only.
  • Use a correctly configured Bitcoin network and verify receiver address network before creating an order.
  • Record payment instructions before opening a wallet confirmation and do not encourage a second payment after submission.
  • Use the target reader or indexer to verify semantic outcome after the on-chain reveal, not merely the HTTP status.

For request fields and reveal API details, continue to the API reference. For payload compatibility, read the payload specification.
