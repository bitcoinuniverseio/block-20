API controller

REST API reference

Order construction, funding instructions, and reveal control.

Endpoints for the current Inscribe implementation. The API builds an inscription order and later reveals it. It does not return a client-signable BLOCK-20 transaction at order creation time.

Direct backend path
/block20/...
Deployment prefix
A reverse proxy may expose the same routes under /api/block20/....
Success status
GET endpoints return 200. Current Nest POST handlers return 201, including a reveal that reports a broadcast failure in its JSON body.
Deployment must define access control. This API reference does not define authentication, authorization, rate limits, or a public custody model. Do not expose mutation endpoints without suitable deployment controls and monitoring.

Create an order

POST /block20/order

Use this endpoint before sending funds. It supplies the generated payment destination, the minimum commit amount, and the exact JSON intended for inscription.

RequestJSON body
{
  "action": "deploy",
  "tick": "BLK",
  "maxSupply": "21000000",
  "limitMint": "1000",
  "description": "Optional description",
  "feeRate": 5,
  "receiverAddress": "<user-controlled Bitcoin address>",
  "outputValue": 546
}
ResponseRepresentative shape
{
  "orderId": "<uuid>",
  "action": "deploy",
  "tick": "BLK",
  "amount": 0,
  "repeatCount": 1,
  "commitAddress": "<server-generated address>",
  "commitAmount": 12345,
  "estimatedCost": "0.00012345 BTC",
  "inscriptionJson": "{...}",
  "blockHash": "",
  "status": "awaiting_payment",
  "network": "mainnet",
  "createdAt": "<timestamp>",
  "expiresAt": "<timestamp>",

Request fieldRequiredCurrent endpoint behavior
actionYesNonblank string. It must resolve exactly to deploy, mint, or transfer when the payload is built.
tickYesNonblank string. It is not trimmed, formatted, length-limited, or checked for uniqueness by this endpoint.
amountNoFinite number or numeric string from 0 through safe integer range. Default 0. Current behavior accepts decimals, so do not assume integer semantics.
maxSupplyNoUsed for deploy max with no numeric validation. Omission yields "21000000" in the payload.
limitMintNoUsed for deploy lim with no numeric validation. If omitted, the public order path uses normalized amount, default 0.
descriptionNoEmitted as des only when truthy. It is not returned as a first-class order field.
repeatCountNoFinite number or numeric string from 1 to 100, floored, default 1. It is not included in the payload. See the lifecycle caveat below.
feeRateNo at runtimeFinite number or numeric string from 1 to 10,000. Default 5. It affects funding, not the payload.
receiverAddressStrongly recommendedNot endpoint-validated. Supply a valid user-controlled address. Empty input causes reveal to fall back to the server-generated commit address.
outputValueNoValues below 330 sats become 0. Values at or above 330 are floored and used as the requested inscription output value.
Persist receiver information client-side. Public order reads intentionally omit receiverAddress, feeRate, retry counters, detailed broadcast errors, and all signing secrets. Retain the destination you showed the user along with the returned order data.

Observe and reveal

Read orders, then use reveal only with an understood outpoint.

The normal flow allows the background monitor to observe a payment and reveal automatically. The explicit reveal endpoint is an advanced recovery or orchestration tool, not proof that the caller controls the funding output.

Read orderGET

Attempt revealPOST JSON body
{
  "commitTxid": "<64-character hex transaction ID>",

Reveal valueRule
commitTxidRequired. Must be a 64-character hexadecimal transaction ID.
commitVoutDefaults to 0. Must be an integer from 0 through 10,000.
commitAmountOptional override. If supplied, must be a positive safe integer amount in satoshis. Numeric strings are rejected here.
Return behaviorA successful signing and broadcast has a non-null revealTxid. A signing or broadcast failure can still be HTTP 201 with revealTxid: null, a broadcastError, and possibly signed txHex.
Repeated reveal after successReturns the saved reveal transaction ID with an empty txHex.
Review outpoint safety before calling reveal. The endpoint validates the shape of the supplied reference but does not preflight that the caller's transaction output belongs to the order's generated commit address. Incorrect references usually surface as signing or broadcast failure.

Read-only services

Tip context and token listings.

These endpoints retrieve upstream data. They are useful for product UI, but neither endpoint establishes a portable protocol state machine.

GET /block20/latest-block

Returns { hash, height } after reading the configured mempool endpoint. A source failure produces a 400 error. Normal mint creation uses this endpoint's underlying server operation internally.

The tip source follows global network configuration, not the supplied receiver address. A mixed-network deployment needs explicit operational review.

GET /block20/tokens

Returns { total, tokens }. Each token contains id, tick, progress, mints, holders, icon, deployDate, maxSupply, and limitMint.

Values are mapped from configured external indexers. Supply and limit are display-formatted strings; progress is an upstream fraction multiplied by 100.

Token query parameterCurrent behavior
tickerTrimmed and lowercased before the upstream query is sent as tick.
startInteger text, clamped from 0 through 10,000,000. Default 0. It is converted to a one-based upstream page offset: floor(start / limit) + 1.
limitInteger text, clamped from 1 through 100. Default 20.
orderByInteger text, clamped from 0 through 100. Default 0.
orderDirOnly normalized asc remains ascending. Any other value becomes desc.
Freshness and fallbackResults are cached for 60 seconds, with up to 256 cached keys. Configured indexers are tried in sequence. A cached result may be returned when all sources fail; otherwise the endpoint returns 503.

Errors and diagnostics

Handle error states as product states.

Do not assume that a 201 response means a reveal broadcast. Store request IDs and distinguish validation errors from an operational reveal failure returned in a successful HTTP carrier.

Representative endpoint messages

  • Request body must be a JSON object
  • Missing required fields: action, tick
  • Unknown BLOCK-20 action: ...
  • Invalid amount., Invalid fee rate., or related numeric error
  • BLOCK-20 order ... not found
  • BLOCK-20 token index is temporarily unavailable - please try again.

Transport envelope

The application error filter normally returns structured information including status, statusCode, error, message, requestId, timestamp, and path.

Responses also carry request metadata headers, including x-request-id and X-Response-Time-Ms. Keep the request ID in support and monitoring records.

Use lifecycle guidance before funding a commit address, and verify the exact emitted bytes in the payload specification.
